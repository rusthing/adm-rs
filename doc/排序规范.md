# 统一排序规范

> 适用范围：adm-svr（axum 0.8 + robotech-rs）与 adm-web（React 19 + CrudPage）。
> 核心原则：**排序值只由服务端分配与维护，前端只提交“同组完整顺序”，不提交具体序号。**

---

## 1. 总则

1. 排序载体只有两种：
   - 平铺实体：`sort_order`（i32，`1..=9999`），组内越小越靠前；
   - 树形实体：`tree_code`（每层 3 位数字，最大 30 位），同时表达层级与兄弟顺序。
2. 新增记录由服务端自动落在**同组末尾**（`max + 1` / 父编码后追加 `001`），客户端传入的排序值一律忽略。
3. 修改记录时服务端清空 DTO 中的排序字段，`sort_order` / `tree_code` 不会被编辑表单覆盖。
4. 调整顺序统一走 `POST /adm/{prefix}/reorder`，请求体是 **id 顺序列表**；服务端按提交顺序整体重算为 `1..n`，不留空洞、不重复。
5. 前端表单不再出现排序字段；列表通过 CrudPage 的 `sortable` 声明开启“排序列”（序号 + 上移/下移 + 拖拽）。

### 1.1 实体清单（以实际 schema 为准）

| 实体 | 表 | 排序载体 | 分组键 | 重排接口 | 前端页面 |
| --- | --- | --- | --- | --- | --- |
| 领域 | `adm_realm` | `sort_order` | 全局一组 | `POST /adm/realm/reorder` | RealmsPage |
| 应用 | `adm_app` | `sort_order` | `realm_id` | `POST /adm/app/reorder` | AppsPage |
| 角色 | `adm_role` | `sort_order` | `group_id` | `POST /adm/role/reorder` | RolesPage |

| 权限 | `adm_perm` | `sort_order` | `group_id` | `POST /adm/perm/reorder` | PermissionsPage |
| 权限分组 | `adm_perm_group` | `tree_code` | `realm_id` + 父编码 | `POST /adm/perm-group/reorder` | PermissionGroupsPage |
| 菜单 | `adm_menu` | `tree_code` | `app_id` + 父编码 | `POST /adm/menu/reorder` | MenusPage |
| 组织 | `adm_org` | `tree_code` | 全局一棵树 + 父编码 | `POST /adm/org/reorder` | 前端暂无页面 |

## 2. 后端约定

实现集中在 `adm-svr/src/svc/adm_sort_svc.rs`，Controller 在 `adm-svr/src/web/ctrl/adm_sort_ctrl.rs`，路由在 `adm-svr/src/web/router/adm_sort_router.rs`。

### 2.1 新增

- 平铺实体：`next_sort_order(db, table, group_col, group_value)`，先对分组加 advisory lock，再取 `COALESCE(MAX(sort_order), 0) + 1`。
- 树形实体：沿用 `next_tree_code`，按“外层隔离列（`app_id` / `realm_id`）+ 父编码”取下一个 `001` 子段。
- 都通过 `#[svc(before_add = ...)]` 钩子写入；DTO 字段标注 `#[fill_by_svc]`，新增请求不需要携带排序值。
- 平铺实体达到 `9999` 时返回业务错误，提示先用重排接口整理。

### 2.2 修改

- `#[svc(before_modify = ...)]` 中把 `dto.sort_order` / `dto.tree_code` 置为 `None`，生成更新语句时跳过该列。
- 结果：客户端即使提交 `sortOrder: 0` 或 `treeCode`，数据库中的值也不会变；已用真实接口验证（详见第 5 节）。

### 2.3 重排接口

```
POST /adm/{prefix}/reorder
Authorization: Bearer <token>
Content-Type: application/json

{ "ids": ["id1", "id2", "id3"] }   // 也兼容裸数组 ["id1","id2","id3"]
```

- `prefix` 必须是**单段**（如 `role`、`role-group`），避免 axum 0.8 对多段参数的解析问题。
- 返回 `Ro`，`extra` 为受影响行数（树形实体会包含被级联改码的子孙行，因此可能大于提交数量）。

#### 平铺实体（`reorder_flat`）

1. 校验：id 非空、无重复；所有 id 必须存在于该表，且属于同一个分组（`group_col` 的值一致，`NULL` 视为同一组）。
2. 事务内对 `adm_sort:{table}:{group_col}={group_value}` 加 `pg_advisory_xact_lock`，再 `SELECT ... FOR UPDATE` 锁住同组全部记录。
3. 校验提交的 id **恰好覆盖同组全部记录**；少传、多传或跨越分组都拒绝，并提示“刷新后重试”。
4. 按提交顺序写回 `sort_order = 1..n`，同时更新 `updater_id`、`update_ms`。
5. 提交同一顺序重复执行，结果完全一致（幂等）。

#### 树形实体（`reorder_tree`）

1. 校验 id 非空、无重复、存在于该表、同一外层隔离域（`scope_col`，如 `app_id` / `realm_id`），并且 `tree_code` 的父编码完全一致。
2. 对表级 key `adm_sort:tree:{table}` 加 advisory lock，并锁住同一父节点下的全部兄弟行。
3. 校验提交的 id 恰好覆盖该父节点的全部兄弟；与当前结构不一致时要求刷新。
4. 两阶段改码，避免唯一键冲突：
   - 阶段 A：按提交顺序把每个兄弟子树挪到临时编码 `~xx`（`~` 开头不会与合法编码冲突）；
   - 阶段 B：按提交顺序落到最终编码 `父编码 + 001..n`，子孙行的后缀随之前缀级联更新。
5. 约束：同一父节点最多 999 个兄弟；`tree_code` 最长 30 位（最多 10 层）。

### 2.4 并发与幂等

- 同一分组的重排被 advisory lock 串行化；事务内先锁行再校验，避免“读到旧结构再写”的竞态。
- 所有校验失败都会整体回滚，不会出现部分更新。
- 如果重排期间有人新增/删除，提交的 id 集合不再等于当前分组集合，接口直接报错，前端提示刷新；刷新后重试即可。
- 重复提交同一 id 顺序不会改变结果（`1..n` 重写，`tree_code` 重算）。

### 2.5 删除后的空洞

- 删除**不会**自动压缩同组序号，也不提供异步“整理任务”。
- 理由：删除是高频操作，自动重排会造成整组写放大，并与并发新增/重排冲突；而 `sort_order` 存在空洞不影响排序结果。
- 需要消除空洞时，直接对当前同组剩余记录调用一次 reorder（按列表当前顺序提交 id），服务端会重算为 `1..n`。

### 2.6 父节点 / 分组变更

- 树形实体：`parentCode` 只在新增时可填（前端 `createOnly`），修改接口会忽略 `tree_code`；因此当前版本不支持通过编辑表单挪动父节点。
- 平铺实体：分组列（如 `app.realm_id`、`role.group_id`）在前端也是 `createOnly`。如果绕过前端直接改分组列，原 `sort_order` 会留在新组里，可能产生重复或空洞；调用方必须在同一事务或随后立即对“旧组 + 新组”分别重排。当前未在服务端强制这一点，属于已知风险（见第 6 节）。
- 未来若开放“移动子树”：需要先移动子树（重写整棵子树的 `tree_code` 前缀），再分别重排旧父节点与新父节点的兄弟列表。

## 3. 前端接入

### 3.1 声明排序能力

`CrudPage` 通过 `sortable` 属性开启，声明类型：

```ts
interface CrudSortable<T> {
  kind: "number" | "tree";             // 平铺 sort_order / 树形 tree_code
  orderValue?: (row: T) => number;     // kind=number
  treeCode?: (row: T) => string;       // kind=tree
  scope?: (row: T) => string | null | undefined; // 分组隔离键
  listOrderBy?: string;                // 拉全量列表时的排序，缺省用 defaultOrderBy
}
```

示例：

```tsx
// 平铺：角色按角色分组隔离
sortable={{ kind: "number", orderValue: (row) => row.sortOrder, scope: (row) => row.groupId }}

// 树形：菜单按应用隔离，组内再按父编码分组
sortable={{ kind: "tree", treeCode: (row) => row.treeCode, scope: (row) => row.appId }}
```

### 3.2 交互行为

- 表头多出「排序」列；单元格显示组内序号、拖拽手柄、上移/下移按钮。
- 拖拽基于 Pointer Events（`setPointerCapture` + `document.elementFromPoint`），鼠标与触摸都可用；只有同一分组内才允许放置。
- 乐观更新：先在本地预览顺序，再调用 `api.reorder(ids)`；成功后 refetch 列表，失败清空预览、重新拉取并 `toast.error`。
- 存在搜索或筛选条件时禁用排序（避免只提交筛选后的子集），悬停提示“清除搜索与筛选条件后可调整排序”。
- 排序列使用**未分页的全量列表**推导分组顺序；页面表格仍按原有分页/筛选展示，不破坏 keyword / select / boolean / date-range / entity 筛选与空值 `--` 渲染。
- 日志类页面（LoginLogsPage）不声明 `sortable`，因此不会出现排序列。

### 3.3 表单

- 所有已接入页面都从 `fields`、`toForm`、`toPayload` 中移除了 `sortOrder` / `treeCode` 输入。
- 新增时由服务端追加到组内末尾；编辑时服务端忽略排序字段。

### 3.4 当前已接入页面

RealmsPage、AppsPage、RolesPage、RoleGroupsPage、PermissionsPage、PermissionGroupsPage、MenusPage；LoginLogsPage 明确不启用。

## 4. 新增实体接入步骤

### 4.1 后端

1. 确认表里有 `sort_order` 或 `tree_code`，并明确分组列（如 `realm_id`、`group_id`、`app_id`）。
2. DTO：给排序字段加 `#[fill_by_svc]`；平铺实体保留 `@range 0..=9999`。
3. Service：
   - 平铺：`before_add` 调用 `next_sort_order(db, "表名", Some("分组列"), 分组值)`；`before_modify` 把 `sort_order` 置 `None`。
   - 树形：`before_add` 调用 `next_tree_code`（带外层隔离列与父编码）；`before_modify` 把 `tree_code` 置 `None`。
   - 钩子函数按实体命名，避免多个 svc 模块导出同名符号。
4. Controller：在 `adm_sort_ctrl.rs` 增加一个 handler，调用 `reorder_flat` / `reorder_tree`。
5. Router：在 `adm_sort_router.rs` 增加 `"/adm/{prefix}/reorder"`，`prefix` 保持单段；路由沿用 Bearer 认证中间件。
6. 运行 `cargo build -p adm-svr`。

### 4.2 前端

1. 确认 `lib/types.ts` 中该实体 VO 已包含 `sortOrder` 或 `treeCode`。
2. 页面 `<CrudPage>` 增加 `sortable` 声明，`scope` 与后端分组列保持一致。
3. 删除表单里的排序字段，并从 `toForm` / `toPayload` 中移除对应键。
4. 设置合适的 `defaultOrderBy`（平铺 `sort_order:asc`，树形 `tree_code:asc`）。
5. 如有独立的分组选项查询，确保下拉数据源也按排序值排序。
6. 运行 `pnpm test`、`pnpm typecheck`、`pnpm build`；需要时在 `sort.test.ts` 补充分组/边界用例。

## 6. 风险与待确认

1. **浏览器级真实拖拽未完成自动化验证**：本次浏览器工具没有原生拖拽手势，拖拽只通过了前端单元测试（`moveSortIdTo`）与代码审查；上移/下移走的是同一条 `submitSort → POST reorder` 链路，已在浏览器验证。建议人工用鼠标与触摸设备各拖一次确认。
2. **无前端页面的实体**：组织、组织类型、人员编码类型在后端已具备自动分配与 reorder 接口，但前端没有注册对应页面（菜单 `component` 未实现），因此未接入 `sortable`；新增页面时按第 4 节接入即可。
3. **直接改分组列的绕过风险**：前端把分组列设为 `createOnly`，但 API 调用方仍可能修改 `realm_id` / `group_id`，导致跨组重复或空洞。当前依赖调用方自觉重排；如需强约束，建议在修改钩子里检测分组变化并拒绝或自动重排。
4. **删除后不自动整理**：序号允许出现空洞，排序结果正确；需要紧凑时调用一次 reorder。若业务要求“删除后立即连续”，需要额外约定。
5. **首页配置未纳入**：`adm_dashboard_widget` 仍是页面内整体保存 `sortOrder`，与本规范不同；如需统一，应改为同一 reorder 接口并移除前端提交的排序值。
6. **重排要求全量覆盖**：分页或筛选状态下不能重排（前端已禁用）；API 调用方必须提交同组全部 id，否则会被拒绝。
7. **树形容量限制**：同一父节点最多 999 个兄弟，树深最多 10 层；超出会返回业务错误。
